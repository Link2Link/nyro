# Kiro Provider 账号池

[English](./kiro-account-pool.md) · [Devin 账号池](./devin-account-pool_CN.md)

## 范围与启用

一个 Kiro OAuth Provider 可以在同一个对外路由目标下管理多个独立授权的账号。原有单账号 Provider 继续可用；新建 Provider 仍沿用现有的 Kiro 登录/导入流程。

在 **Providers → Kiro → 管理账号**（或展开的 Provider 设置）中先保存 **账号池调度设置**，再点击 **添加账号**。认证方式仍为 Google、GitHub、AWS Builder ID、IAM Identity Center 和凭证导入。导入支持现有的 Kiro IDE/CLI 凭证格式和静态 API Key，浏览器/设备登录选项与代理设置均保留。

每个账号拥有独立且不可变的 ID，以及别名、优先级、启用状态、凭证代次、用量观测和调度状态。优先级数值越小越优先。重新授权/导入只针对某个账号及其预期版本；移除账号只清除该账号的凭据，并保留断开记录以阻止延迟回调恢复授权。已断开的记录不可复用，需要时请添加新账号。若账号已有身份信息，重新授权时必须是同一身份。

## 上游客户端标识

新的 AWS Builder ID / IAM Identity Center 设备登录使用 `clientName = "Kiro IDE"` 注册。Google/GitHub 设备登录保留现有的 `clientId = "kiro-cli"`，不会执行 AWS 客户端注册。授权、令牌刷新、profile 发现、生成和用量共用一个身份构造器：参考 kiro-manager-lite 使用 `KiroIDE-0.12.333-<machine-id>` 与流式 SDK 兼容版本 `1.0.39`。Node 版本字段是兼容声明，不代表 Nyro 启动了 Node 进程。每次调用声明单次尝试并生成独立的 invocation UUID；生成请求另带 `x-amzn-kiro-agent-mode: vibe`。

机器标识为进程内缓存的主机哈希，与 profile ARN、客户端注册和令牌轮换无关。Linux 优先读取规范化后的系统 machine-id；其他/回退路径使用主机名，无主机身份时使用进程内稳定的随机值。如需重启后保持一致，应保持容器 machine-id/主机名稳定。不会发送原始设备标识，也不模拟 TLS 指纹。

运行时服务区域将 `eu-*` 映射到 `eu-central-1`，其他区域映射到 `us-east-1`；AWS OIDC 保留原注册区域。OAuth 生成使用 Amazon Q。显式 profile 始终优先；Builder ID/社交账号缺少 profile 时，仅在请求中使用参考实现的兼容默认值，不会存为已验证的 `subject_id`。Enterprise/IdC 使用发现的真实 profile，不猜测其他组织的 ARN。导入的 `ksk_` API Key 使用 Kiro runtime/management 端点、声明 `tokentype: API_KEY`，且绝不发送 OAuth profile。

已有 AWS 注册会保留创建时的名称：升级或刷新令牌**不会**把 `Nyro Kiro Gateway` 自动改名。升级后需对受影响账号重新授权，以创建新的注册；导入凭证在重新授权前也保留原注册。重新授权不会删除旧的上游授权记录，可在上游账号设置中检查/撤销旧记录。

这些值与参考实现对齐，并非经过完整抓包验证的当前官方客户端行为。授权类型、scope、凭证存储和生成重放安全边界保持不变。本次不增加盲目生成重试、跨区域试探、TLS 模拟或企业 profile 猜测。名称和 HTTP 请求头一致，不代表遥测或执行行为完全一致；真实浏览器登录和生成请求仍需单独验收。

普通的用量 HTTP 403 不再永久作废账号：只有 HTTP 401 或明确的令牌过期/无效/账号暂停证据才会标记失效。刷新 HTTP 400/403 也需要明确的 OAuth 拒绝码才会作终态处理；HTTP 401 仍为终态。诊断保留脱敏白名单错误类型和固定原因分类，不保存原始凭证或任意上游文本。升级与用量轮询不会自动清除历史 `auth_invalid` 标记；应确认上游拒绝原因后重新授权。

通用用量界面区分账号池实际就绪原因（如需要登录）与真正额度耗尽，即使兼容的调度状态仍为 `quota_exhausted`。只有真正额度的 `reset_at` 才显示重置倒计时；`next_check_at` 不代表恢复承诺。

## 调度与安全切换

实现复用 Devin 的有界账号注册表、通用管理接口和现有凭证存储，但不使用其套餐分类：

- 默认策略：轮询，开启会话粘性，粘性有效期 3600 秒，单个请求最多尝试 3 个不同账号，付费兜底关闭。
- 也可选择 `fill_first`。在最佳成本等级和优先级分组内，有效的会话绑定优先于轮询。
- 优先使用套餐内额度，其次是用量未知的账号，最后才是明确允许的付费超额。已停用、已断开、认证被拒和硬性额度封锁的账号会被排除。模型冷却与熔断按账号及凭证代次隔离。
- 付费兜底必须**同时**满足 `reserve_policy = fallback` 与上游账号的 `overage_enabled`。这只控制调度选择，不是上游账单硬限额：一次请求仍可能在生成过程中耗尽剩余额度。
- 每个账号的成本等级在准入时记录，并在提交前重新校验。若并发的用量观测使选中账号降级（例如从套餐内额度变为付费超额），该账号不会被提交，而是重新排序，让仍有套餐内额度的账号优先。
- 账号专属的凭据、区域、profile ARN 与 OIDC 注册信息作为不可变的请求快照一同传递，不会修改任何全局"当前令牌"。
- 只有明确的认证/计费拒绝，或可识别的结构化 AWS 拒绝，才允许在执行前切换到其他账号。裸的代理 403/429/503、提交后的超时，或 HTTP 已接受后出现的异常，都不构成重放依据。流式失败仍会更新对应账号的健康状态，但不会重放已输出的内容或缓冲中的工具调用。
- 与账号绑定的不透明续接不会跨账号迁移。请求的总截止时间、取消信号以及最多 8 次上游生成的预算依旧生效。

认证被拒需要重新授权。额度被拒后会保持封锁，直到更新且完整的观测确认套餐内额度可用，或明确允许付费超额。旧凭证代次的失败不会作废新的凭证。

## 令牌刷新

现有的社交登录与 AWS OIDC 刷新协议保持不变。后台刷新与请求时刷新均按精确的 `(provider_id, account_id, status_version)` 操作，而不是含糊的 Provider 级凭证。即将过期（提前 5 分钟）的令牌会在请求准入前刷新；静态 API Key 无需刷新。

每个账号使用独立的单飞锁，并通过存储层 CAS 发布刷新结果。刷新在独立任务中执行：客户端取消或请求超时只会停止等待，不会遗弃已占用的 `refreshing` 租约，也不会丢失上游已轮换的 refresh token。刷新中的账号仍是账号池成员，请求会等待该租约，而不是报告账号池为空。账号别名、优先级、启用状态和最新额度状态都会保留。并发的重新授权、停用或断开会阻止延迟的刷新结果写回。某个账号刷新失败不会覆盖其他账号，也不影响健康账号被选中。上游明确的认证拒绝不会被只读的用量查询或常规刷新悄悄清除。

## 按 Kiro 实际用量，而非 Devin 单位

每个账号展示 Kiro 识别出的套餐，以及各资源条目的实际 `used`、`limit` 和重置/到期时间。基础额度、有效赠送额度与有效试用额度在**同一资源内**累加；不同资源各自独立约束。显式的零额度视为已耗尽；缺失用量视为未知，而非零使用。

赠送/试用到期不算作补充额度的重置。即使之后没有新的成功查询，已到期的额度也会被排除出调度。刷新失败或返回不完整时，保留最后一次可信观测并标记为过期；缺少此前已观测资源的部分响应不能解除额度封锁。

界面展示账号池账号数量、**按资源汇总的账号池合计**，以及每个账号的资源用量。账号池合计对已启用且未断开的账号，按同一资源累加各自实际的 `used`（不超过其上限）与 `limit`，并展示由此得到的已用百分比、剩余百分比、用量覆盖（有观测的账号数 / 成员数）、旧数据账号数，以及最早的账号重置时间（所有账号重置时间一致时标记为共同重置）。不同资源之间绝不合并。其匀速参考线仅用于展示：取每个账号朝其自身重置时间的月度窗口进度，按该账号额度上限加权；只要有账号缺少重置时间就隐藏。界面不会虚构日/周窗口、Pro 等价单位或统一重置时间。Provider 用量接口也会通过通用的 `tiers` 字段提供仅用于展示的合计（详见下文）；调度仍按账号进行。连接测试分别检查已启用的账号，不消耗生成额度，任一账号通过即视为成功；模型建议列表不代表账号一定有对应权限。

## 每账号网关历史用量

每个账号的操作区域增加 **全部记录 / 本月** 紧凑统计，分别显示总 Token 和等价 API 估算金额。本月从浏览器本地时区的 1 日 00:00 开始，与 Kiro 额度重置时间无关。复用[账号用量接口与统计规则](./devin-account-pool_CN.md#每账号网关历史用量)：按稳定账号 ID 归属、包含保留日志中的重试/失败尝试、缓存不重复计数、采用当前参考/手工价格、明确标注缺价/部分估算、按原始币种分别展示。日志保留期和删除操作会减少历史覆盖，这不是永久累计台账。

Kiro Token 数来自上下文比例/本地内容估算（缓存读取也是假设值），并非上游实际扣除的 Credit。Token 和等价 API 金额不会替代上面的资源额度观测；统计接口只读，不改变配额或调度。

## 接口与持久化

现有账号接口同时支持 Devin 与 Kiro：

- 读取/配置 Provider 账号池。
- 初始化绑定到账号的登录会话（可选携带类型化的 `kiro` 登录选项）。
- 绑定已完成的会话；按预期版本更新别名/优先级/启用状态；断开账号；刷新单个或全部账号的用量。

公开账号 DTO 新增可选字段 `kiro_usage`；Kiro 账号池视图带有 `kind = "kiro"`，不含 Devin 的日/周窗口，也绝不包含 access token、refresh token 或 OIDC client secret。HTTP 与桌面端适配层均委托给核心管理服务。

`GET /api/v1/providers/usage` 与 `GET /api/v1/providers/:id/usage` 返回 `kind = "kiro_plan"`。对于多个已启用且未断开的账号，`usage.tiers` 按资源输出合计：只有一种资源时名称为 `monthly`，否则为 `kiro:<resource>`。已用百分比为 `sum(套餐内已用量) / sum(额度上限) * 100`，不是各账号百分比的平均值，也不是按套餐名称估算。例如 1308.87 / 2000 与 176.56 / 1000 Credit 会得到一条 49.5143% 的总用量。总额度为零时显示 100% 已用。基础额度、有效赠送/试用额度沿用界面的单账号规则；付费超额不计入套餐内已用量。

只有所有成员均有该资源的有效观测时才输出总量；缺失观测不会当作未使用额度。最后一次可信的旧观测可以参与汇总，其 `stale` 标记仍保留在 `usage.account_pool.accounts` 中。只有所有参与账号都具有相同且已知的基础额度重置时间时，才填充 `tiers[].resets_at`，否则返回 `null`（不虚构共同重置时间或误导性的匀速参考线）。账号明细仍保留在 `usage.account_pool.accounts[].kiro_usage`；单账号响应保留已有档位与信息性额度明细。`dsh-nyro-usage` 等通用客户端无需解析账号明细即可直接显示总用量。合计绝不写入配额注册表或参与账号选择；`usage.scheduling` 仍由各账号的实际可用状态决定。

本次没有数据库结构迁移。内存、SQLite、PostgreSQL 和 MySQL 均复用现有 `provider_oauth_credentials` 的多账号记录与设置存储。与 Devin 相同，每个账号池数据库应只对应一个活动网关实例；会话与粘性协调仅在进程内进行，并非分布式调度。

## 验证与运行限制

针对性回归测试覆盖账号选择、实际额度与到期额度、账号级失败隔离、刷新隔离与过期写回防护、登录/导入目标绑定、管理 DTO 脱敏以及前端控件。真实账号浏览器登录、线上生成请求和部署需单独验收。测试不得修改生产数据库；可选的 PostgreSQL/MySQL 测试需使用专用的一次性数据库。
