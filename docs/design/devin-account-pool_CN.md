# Devin 单 Provider 多账号池设计

状态：**首版实现已写入工作树，尚未部署**。英文规范：[Devin Provider Account Pool](./devin-account-pool.md)。领域术语：[Domain Context](../../CONTEXT.md)。

## 本次实现边界

- 已实现账号存储/迁移、Pro/Max 校验、账号管理、额度汇总、优先级轮询/顺序填充、会话粘性、账号级失败反馈、安全切换、HTTP/Tauri 和 WebUI。下文保留设计依据，“当前代码事实”及旧行号指开发前基线，不代表修改后那些行仍有原限制。
- **包含 Devin 账号池的数据库只运行一个 Gateway 实例。** 登录 session、档位修改/退出协调与调度状态是进程内机制；多个 PostgreSQL/MySQL 写入实例共同管理账号池不在首版支持范围，账号 CAS 不等于跨进程 plan/fence 发布事务。这与禁止新旧二进制混写是两个独立限制。
- 用量明确标注“估算”：校验套餐/窗口及重复 token，但未新增独立身份 RPC，不能审计不同 token 是否对应独立订阅或绝对套餐容量；未增加跨 Provider 重复账号告警。
- 单账号并发上限、分布式 lease 和配额加权调度留待后续；首版没有可配置的单账号并发限制，模型健康许可仍提供熔断半开控制。
- 多账号时旧 Provider-only 复制/探测/测试明确返回歧义，不随机选账号；已配置池可发现静态模型目录。未新增仅复制池配置的专用动作。
- 配置导入导出保留池策略和档位，不导 OAuth 凭据或账号描述列表；保留登录需要备份数据库。未配置池前，旧单账号仍可通过原登录流程重新授权。
- 验证使用内存/mock 上游和临时数据库；未使用真实 Devin 账号登录/聊天，未迁移生产数据，未替换正在运行的应用。

## 一、结论与边界

采用 **Provider 外层路由 + Account 内层调度**。用户只配置一个 Devin Provider，可以在其下多次登录不同账号；模型绑定仍指向原 Provider，不随账号数量增长。

**修订要求：同档位账号池。** Devin Provider 必须明确选择 `account_pool.plan = pro | max`，池内账号档位和对应窗口的单账号标准额度一致。Pro 对外统一显示一个日额度和一个周额度；Max 只显示一个周额度。在这个约束下，各账号额度可叠加后归一化为账号池百分比，替代之前“只显示账号数量、不显示池百分比”的方案。这里的 Pro/Max 窗口规则是本功能采用的产品约束，并非现有解析器已经硬编码这两个套餐。

```text
客户端请求
  → 现有模型/Provider 路由
  → Provider 内筛选可用账号
  → 会话粘性 + 优先级 + 轮询
  → 固定本次请求的账号凭证快照
  → 现有 Devin Connect/protobuf 转发
  → 将配额、鉴权、冷却和请求结果反馈给对应账号
```

不采用以下方案：

- 不为每个账号创建隐藏 Provider，避免复制模型绑定、权重和配置。
- 不把 OAuth session token 塞进现有 API Key 池，避免破坏鉴权生命周期。
- 不为每个请求修改 Provider 的“当前账号”，避免并发串号。
- 不直接搬用 CLIProxyAPI 的调度器；复用 Nyro 的 quota、health、dispatch 和原生协议实现。

首期仅 Devin 开放多账号。其他 OAuth driver 仍限制一个账号；Provider 固定官方地址、协议和代理策略，账号暂不支持独立代理。自动注册账号、跨 Provider 共享账号仓库、分布式并发额度管理不在首期范围。

## 三、领域与数据结构

### 3.1 分清三个概念

- **Provider**：路由目标和共享配置，包含模型、协议、官方地址、代理、外层权重。
- **Provider Account**：Provider 下的独立授权身份，包含登录凭据、账号启用开关、套餐与配额。
- **Account Pool**：该 Provider 内可参与调度的账号集合，不是页面上的 Provider 品牌分组。

账号的四个维度不能混成一个 status：

1. 管理员是否启用；
2. 授权是否有效；
3. 套餐/余额是否允许调度；
4. 当前模型是否在临时冷却或熔断。

因此 A 账号额度耗尽时：只暂停 A，不修改 A 的启用开关，也不禁用整个 Provider。

### 3.2 升级原凭据表，不维护两套真源

建议将 `provider_oauth_credentials` 从 Provider 主键升级为账号主键：

```text
account_id                 稳定本地 ID，主键
provider_id                Provider 外键，可对应多行，有索引
label                      账号别名
is_enabled                 管理员启用开关
priority                   数值越小优先级越高，默认 0
identity_key?              可验证的上游身份，可空
credential_fingerprint     内部凭据摘要，不返回前端
原有 token/driver/status/status_version 等字段
```

其他 OAuth Provider 迁移后也有一个默认账号，但其 driver 暂不允许第二个账号。单账号限制必须在事务内检查，不能先查数量再插入。

**身份与去重：**

- 本地 `account_id` 不依赖邮箱、用户名、token 或可能为空的 `subject_id`。
- 相同 token 的重复添加用规范化后的摘要检测，返回已有账号，不再创建候选。
- 能从认证后的上游响应确认身份时，按 driver + subject + 必要的组织范围去重；发现同身份的新 token，应明确重新授权已有账号。
- 当前 Devin 状态解析刻意忽略个人字段，身份探测是新增能力，不是已经存在的能力。
- 无法确认身份时允许别名管理并标记“身份未确认”；不能宣称 token 摘要能识别同一用户的所有登录。
- 跨 Provider 检测到重复账号只提示共用额度，不自动合并，也不擅自修改其他 Provider。

### 3.3 Provider 档位与入池校验

- 新建 Devin Provider 明确选择 `pro` 或 `max`，不能对未知套餐静默默认 Pro。非空账号池不能通过普通编辑直接改档位；需要先移除/转移账号，或显式执行全池重新校验的原子重分类。
- 添加/重登时通过认证后的状态响应校验套餐名和适用窗口；后台刷新持续复查。Pro 期望日+周窗口，Max 期望只有周窗口。Max 的日额度是“不适用”，不是 0% 或 100%。
- 当前解析器读取 `plan_name`、隐藏标记和适用窗口，并不按 Pro/Max 字符串硬编码。新增明确的白名单规范化/校验层：不认识的名称或不兼容权益标为 `plan_unverified` / `plan_mismatch`。用户选 Max 不能把上游实际返回的日限制强行忽略；缺少必需窗口也不能伪造数据。
- 添加错档位账号直接拒绝。已有账号升级/降级后移出调度和额度汇总，显示档位不匹配，不擅自改变 Provider 档位。一次查询失败不等于档位改变，保留最后确认的归属。
- 容量按独立上游权益计数，不按 token 数计数。已知同账号重复登录不能扩大池容量；无法确认独立身份或等容量时标注“估算”，不能声称已核实容量。即使套餐名相同，若发现实际权益不同，先分池，不在首期引入隐含加权。

### 3.4 凭据一致性与持久化

所有 get、绑定、重登、断开、refresh CAS 改为账号寻址，并验证 Provider 归属。

一次请求固定持有：

```text
(provider_id, account_id, credential_version, token)
```

禁止执行途中重新取 Provider 的“当前 token”。

保留现有断开后的清密钥 tombstone 和递增版本；旧请求、旧状态查询、旧回调不能把已退出的账号恢复。绑定替换应在事务内获取 before/after，或要求 expected_version，避免旧快照补偿覆盖中间发生的新登录。

调度方面：

- 持久化明确鉴权失效、账号级硬配额阻塞、原因、reset 提示、最近权威观察及关联凭据版本。
- 轮询游标、短暂限流冷却、会话映射和进行中请求数可保存在内存。
- 只在关键状态变化时写入硬阻塞状态，不为每个请求写库。
- 重启后已耗尽账号仍等待权威复查，不因状态丢失又被打一次。
- 重登修复鉴权问题，不自动清除同一上游身份的额度耗尽。
- 查询结果除凭据版本一致外，还必须新于它要覆盖的状态；耗尽前启动、耗尽后才返回的旧查询不能“复活”账号。

## 四、登录和管理操作

必须区分：

| 操作 | 语义 |
| --- | --- |
| 添加账号 | 建立新登录 session，成功后追加账号，不覆盖旧账号。 |
| 重新授权 | 绑定指定 Provider、账号和预期版本，只替换该账号授权。 |
| 刷新用量 | 查询 `GetUserStatus`，不调用 Devin 不支持的 token refresh。 |
| 启用/停用 | 改管理员意图，不删除凭据或配额记录。 |
| 断开/移除 | 清理该账号凭据，阻止旧回调写回，不影响兄弟账号。 |

复用已有 PKCE、state 校验、粘贴 token、`prompt=select_account` 和 session 单次消费机制。登录意图 `add_account` / `reauthorize_account` 必须由服务端保存，不能由前端在回调结束时随意改目标。

新增账号授权完成后做状态探测、Provider 档位/窗口校验和可支持的身份探测：明确无效的凭据、档位不匹配或档位未确认的账号不能参与调度；网络失败显示未验证并安排重试，不误判成额度耗尽，也不静默显示可用。旧版本迁移的已连接账号保留授权状态；档位未确认时保留原单账号路径，但暂不允许扩池或声称统一容量。

若重新授权得到的已验证身份不是原账号，拒绝账号不匹配或让用户明确按新账号添加，不能沿用原账号配额历史。全池断开需要独立确认，并通过 Provider 级版本隔离取消旧的待完成添加操作。

## 五、两级调度和会话粘性

### 5.1 外层仍选择 Provider

模型绑定、Provider 权重、原有优先级和显式 fallback 保持不变。增加 5 个账号不等于增加 5 个外层路由条目。

Provider 状态是账号可用性的聚合：至少一个账号可服务，Provider 就不因其他账号耗尽而被停用。区分无账号、全部停用、需要登录、额度耗尽、临时不可用，不能全部报为配额不足。

现有 `usage` 策略按以下层次接收聚合结果：

1. 有可用套餐账号：正常层；
2. 无已知套餐余量、但有可用未知用量账号：unknown 层；
3. 只剩允许使用的付费余额账号：reserve 层；
4. 无账号可用：不可用层。

需要 Provider 用量权重时，仍取当前可用非 reserve 账号的最高**最终调度分数**，包括现有 `dynamic_weight(rate) × window_boost(window)`，不直接拿展示用的池百分比代替账号评分，也不按账号数自动放大外层权重。**路由评分与下面定义的同档位池额度汇总是两个输出**：额度可以相加展示，但不能给汇总百分比配一个虚构的共同 reset，送进原本面向单账号的评分器，更不能只看池百分比判断可用性。

保留显式 fallback backend 的原有最后顺序；现有 reserve 降级仅影响 `usage` 策略，不借本功能悄悄重排其他所有路由策略。

### 5.2 内层选择账号

首期推荐算法：

```text
授权有效且启用、档位已验证匹配、模型可用
 → 排除已知耗尽、冷却、熔断和本请求已尝试账号
 → 套餐额度优先，其次未知用量，再次允许的付费余额
 → 选当前层中最高配置优先级
 → 有有效会话绑定则优先使用
 → 同级账号轮询
 → 原子取得请求槽位并复核账号版本
```

默认 `round_robin`，另提供 `fill_first`，暂不堆叠复杂调度策略。未来若需要配额加权，可复用现有 quota scoring。

建议配置示例（**新设计，不是现有接口**）：

```json
{
  "account_pool": {
    "plan": "pro",
    "strategy": "round_robin",
    "session_affinity": true,
    "affinity_ttl_seconds": 3600,
    "max_account_attempts": 3,
    "reserve_policy": "disabled"
  }
}
```

新建池默认不主动走付费余额；旧 Provider 迁移显式保留原本的余额兜底行为。用户可以选择 `fallback`。套餐/付费层级优先于粘性，不能为了粘住 A 而在 B 有套餐额度时继续烧 A 的余额。

**注意：这不是上游账单硬限额。** 缓存显示有套餐额度时，一次请求可能用完额度并被上游自动从余额扣费。严格禁止扣费必须同时关闭上游 overage；不能在 UI 承诺网关策略能实现绝对零支出。

可选单账号并发上限默认不设置，以免改变旧行为。启用后使用原子 lease，直到整个流结束/取消才释放；本地槽位满不计入上游健康失败。

### 5.3 会话粘性

绑定键：

```text
(调用方身份或 Nyro API Key ID, provider_id, logical_session_id) → account_id
```

用有容量上限的 TTL/LRU 缓存。一次解析逻辑 session，同时用于账号选择和 Devin 编码；不拿原始 prompt/token 当缓存键，没有明确 session 时正常轮询，不把所有匿名请求粘成同一会话。

当前 [Devin session ID 生成](../../crates/nyro-core/src/provider/devin/request.rs#L638-L675) 需要从编码器中提取出边界，并让上游 session/cascade ID 带账号命名空间，避免换账号继续使用另一个账号的上游会话标识。

- 绑定账号耗尽、停用、失效时解除绑定。
- 暂时并发满可给本次请求选其他账号，不必永久改绑。
- 并发首轮请求需要原子建立临时绑定，成功后确认，失败后释放，避免竞态分流。
- 仅有上游 opaque continuation、无法还原完整历史的请求，不能跨账号续接；不删除签名或伪造历史来强行换号。
- 首期粘性与并发计数是单进程范围；共享数据库不代表多副本之间也自动共享这些状态。

## 六、错误隔离与安全切换

在 HTTP/Connect 错误脱敏之前提取有限、安全的结构化信息：

```text
scope: request / account / account_model / provider_model / transport
reason: auth_invalid / daily_quota / weekly_quota / rate_limited /
        model_forbidden / capacity / request_invalid / transport_unknown
retry_after?
rejection_evidence: not_submitted / explicitly_rejected / execution_unknown
```

错误原文可能带请求内容或 token，不能为了分类而写入日志。单看 403/429 不足以判断全账号失效或额度耗尽。

| 结果 | 状态影响 | 能否换账号 |
| --- | --- | --- |
| 明确凭据失效/撤销 | 仅该账号需要重新登录 | 明确拒绝且未提交给客户端时可以。 |
| 明确日/周额度耗尽 | 整个账号暂停，并触发该账号用量刷新 | 有明确拒绝证据时可以。 |
| 普通限流、容量拒绝 | 最窄可信范围的短冷却 | 仅证明执行前拒绝时可以。 |
| 某模型无权限 | 账号+模型暂不可用 | 其他账号有能力且安全时可以。 |
| 请求参数错误 | 不处罚账号 | 直接返回，不轮遍全池。 |
| 提交后断网/超时、执行情况未知 | 记录传输错误 | 不自动重放。 |
| 已输出文本/工具调用后报错 | 记录失败和后续账号状态 | 不拼接其他账号的结果。 |
| 客户端取消/本地槽位不足 | 健康 neutral | 不记上游失败。 |

账号模型健康键改为 `(provider_id, account_id, protocol, actual_model)`。公共上游故障仍可走共享传输层处理，避免同一个服务挂了还轮遍全部账号。用量恢复不能清掉独立的模型冷却；账号鉴权失效必须重新授权才能解除。

健康展示也要聚合：不能因为任一账号的 circuit 打开，就把仍有其他账号可用的 Provider 标为不可用。

### 原生流式通道的强约束

**未收到首字节、未向客户端输出，不等于上游没执行。**

换账号必须同时满足：

1. 下游尚未提交响应，允许替换；
2. 没有模型输出或工具执行证据；
3. 请求尚未提交，或有经过测试的 Devin 明确执行前拒绝证据；
4. 请求可由支持的完整历史重建，不依赖原账号的 opaque 状态；
5. 尝试预算和共享 deadline 仍有余额。

HTTP 200 后的 Connect trailer 错误不能一概重试。只有严格证明为执行前鉴权/配额拒绝的情况才允许；其他情况保留 `Never`。同时修正当前 native 分支按最终 401/403 就绕过 `Never` 的做法，使用来源和阶段明确的证据。

默认一个 Provider 最多尝试 3 个不同账号；另增加请求级全局生成尝试预算，建议初始上限 8，覆盖账号切换、Provider 切换、API Key 切换及同目标重试，共用请求 deadline 和已尝试集合。当前 AttemptCount 只是计数，不是已经存在的预算控制。

账号池用尽但仍安全时，继续现有外层 Provider fallback；执行不确定时，即使还有健康账号也返回失败。不能把外层 N 次与内层 M 次重试相乘。

## 七、配额观察、恢复与 Provider 用量展示

复用现有规则和用量刷新机制，只把 key 下沉到账号：

- 健康账号约 5 分钟刷新，加入抖动。
- 使用付费余额的账号约 1 分钟刷新，避免余额快速耗尽后仍继续选用。
- 已耗尽账号按“可信 reset + 宽限”与有上限的提前恢复检查二者取早；建议提前恢复检查约 5 分钟。
- 无 reset 时短周期复查并退避，不能永久冷却，也不能到点自动假定恢复。
- 需要重新登录/已停用账号不做 chat 重试，可暂停后台检查。
- 查询失败保留最后权威状态，不把超时当零额度或恢复。

每账号 singleflight，配合全局有限并发；手动与后台刷新共用锁。Native 429 必须单独触发账号级刷新，因为当前 native 提前返回，不经过普通转发分支的 429 refresh hook。

日/周“适用窗口”才参加判断：隐藏、未适用、unlimited 不要求大于零；适用窗口省略数值按 proto3 零处理。已有用量解析规则不变。明确上游额度拒绝优先于旧的正余额快照，等待更晚的权威查询解决冲突。

**时间到了只触发复查，权威结果确认后才恢复。** 同一账号多个窗口耗尽，全部相关阻塞都解除才恢复；跨账号 Provider 则任一候选恢复即可服务。

### 7.1 同档位额度统一计算

对每个适用窗口，设参与容量统计的账号数为 `N`，每个账号剩余百分比为 `r_i`（0～100）。把该档位一个账号完整的日或周额度定义为 **1 份账号额度**：

```text
总额度份数       = N
剩余额度份数     = Σ(r_i / 100)
已用额度份数     = N - 剩余额度份数
池剩余百分比     = 剩余额度份数 / N × 100%
池已用百分比     = 100% - 池剩余百分比
```

也可以先相加百分数的数值，但总容量是 `N × 100`，不是 100。同档位且等容量时，各账号百分比的算术平均等价于“先叠加额度、再按总容量归一化”。上游没有提供 Token/ACU 的绝对额度时，不伪造这些单位。该结果是各账号**当前额度窗口**的快照，不是某个统一自然日/自然周内的累计消耗。

例如三个 Pro 账号：

| 账号 | 日剩余 | 周剩余 |
| --- | --- | --- |
| A | 60% | 20% |
| B | 30% | 50% |
| C | 90% | 80% |

统一输出：

- 日额度：已用 **40%**，剩余 **60%**，相当于剩余 **1.8 / 3 份 Pro 日额度**。
- 周额度：已用 **50%**，剩余 **50%**，相当于剩余 **1.5 / 3 份 Pro 周额度**。
- 若是三个 Max 账号，周剩余相同，则只输出上述周额度；日额度字段为 `null` / 不适用，UI 不画日进度条。

### 7.2 分母和数据完整性

- 容量成员为：已启用、未移除/断开、最近已确认档位匹配的账号。**耗尽账号仍计入分母**；短冷却、模型熔断、后续需要重登也不因暂时无法调度而缩小分母。授权/调度状态另外统计。
- 停用、移除、断开、已确认档位不匹配的账号不参与容量统计，显示排除数量与原因。容量成员变化时分子和分母一起变化，这叫容量调整，不是假装刚刚消费或恢复额度。
- 刷新失败时沿用同一权益版本的最后可信快照并标注 stale/估算；不能跨身份或档位变化沿用旧快照。未知值不能填成 0 或 100。
- 若 N 个成员中有账号从未获得快照，保留 `total_units = N` 和 `known_accounts / N`，整体完整百分比及总量返回 null。UI 显示“更新中（2/3 账号）”，可补充明确标注的已知小计，但不能偷偷改用已知账号数量当分母冒充整池用量。`N = 0` 显示无有效池容量，而非已用 0%/剩余 100%。
- 每窗口返回 `total_units`、`used_units`、`remaining_units`、`used_percent`、`remaining_percent`、数据覆盖率/陈旧标记；可调度账号数单独返回。展示用汇总不能被写入旧的单账号 Provider quota 判断器，调度仍以账号级状态为准。

### 7.3 额度汇总不等于可调度性

两个 Pro 账号的极端情况：

```text
A：日剩余 100%，周剩余 0%
B：日剩余 0%，周剩余 100%

池日剩余 50%，池周剩余 50%，但套餐可用账号数 = 0
```

两条汇总进度条都是真实的额度统计，但不能把 A 的日额度借给 B。此时仍展示统一用量，同时醒目标注“当前无可用套餐账号”；若有允许的余额兜底，再单独显示 reserve-only。也不使用 `min(日百分比, 周百分比)` 伪造可调度额度，因为日和周不是相同容量单位。

### 7.4 重置时间

同档位账号不要求同一时刻重置。保留各账号 reset，同时返回 `next_reset_at`、受影响账号数和 `reset_mode = staggered | aligned | unknown`。

只有全部成员上报相同时间，才显示共同重置时间；否则写“下次账号额度重置：2 小时后（1/3 账号）”，不能写“整个池 2 小时后恢复”。某账号到点且上游确认后，只增加该账号对应额度。付费余额与套餐日/周份数始终分开。

## 八、接口、界面和可观测性

业务逻辑仍在 nyro-core AdminService，server HTTP 和 Tauri IPC 只做入口适配。建议新增账号列表、账号登录 session、绑定、修改启用/优先级、重登、用量刷新、断开等接口，全部校验 `(provider_id, account_id)` 归属。

登录 session 应携带 intent 与 expected version；敏感 DTO 不直接序列化 OAuthCredential，仅返回白名单字段。旧 Provider-only 操作在多账号时返回明确 `AMBIGUOUS_ACCOUNT` / HTTP 409，而不是选第一条或删全部；在消耗登录 session 之前检查歧义。

Provider 配置增加必选 `Plan: Pro | Max`。卡片复用单账号供应商的额度进度条形式，主视图直接展示统一用量，并附档位、容量与可用账号数：

```text
Devin · Pro                              3 个账号 · 3 个可用
日额度  [已用 40%]   剩余 60%              1.8 / 3 份账号额度
周额度  [已用 50%]   剩余 50%              1.5 / 3 份账号额度
下次账号额度重置：2 小时后（1/3 账号）       [管理账号]
```

Max 完全隐藏日额度行。进度条沿用现有已用/剩余方向，明确数据不完整、陈旧和档位不匹配状态；不要只凭两条百分比给 Provider 标为可用。展开账号面板保留明细（Max 隐藏日额度列）：

| 别名 | 授权 | 调度 | 日剩余 | 周剩余 | 付费余额 | 操作 |
| --- | --- | --- | --- | --- | --- | --- |
| Personal A | Connected | Available | 62% | 31% | $0 | 刷新用量、重登、停用 |
| Personal B | Connected | Quota exhausted | 0% | 15% | $0 | 刷新用量、停用 |
| Team C | Needs login | Unavailable | — | — | — | 重登、移除 |

同时显示 reset、上次成功观察时间和 stale 标记。默认文案使用英文，中文通过 i18n 提供。保留当前工作树里的 Provider 分组和更多操作改动，不回退这些用户修改。

日志沿用现有 attempt/final result 结构，补充安全的账号 ID、别名快照、选择原因、切换序号、错误范围；一次客户端请求仍只有一个最终结果。禁止输出 token、原始鉴权响应，不用邮箱做指标 label。

## 九、迁移与兼容

1. 停止旧版本读写进程，做真实数据库一致性备份；UI 配置 JSON 不是 OAuth 凭据备份。
2. 原表迁移每行到确定的 legacy account ID，保留 token、status、status_version，包括已断开的 tombstone。
3. Provider ID、模型绑定保持不变，旧账号默认别名 `Default account`；旧余额兜底策略显式保留。档位只能从已确认且窗口兼容的状态推断，否则保留旧单账号路径，显示“需要选择套餐”，在用户选择并验证 Pro/Max 前不允许扩池或宣称统一容量，不能用缺数据推断 Pro。导入导出同步保存选定档位。
4. **必须同时修正旧凭据启动回填。** 当前从 Provider 旧字段回填凭据依赖 `provider_id` 唯一冲突幂等。取消唯一约束后应使用一次性迁移标记/稳定 legacy ID/包含 tombstone 的存在性检查，防止重复导入或退出后旧 secret 复活。
5. runtime、探测、模型目录、用量、复制和管理操作统一传 account_id；管理状态查询不偷偷跑随机账号选择。
6. 旧接口仅在账号无歧义时兼容，包括停用/失效账号的歧义判断；多账号统一拒绝需要目标账号的旧调用。全部断开是独立确认动作。
7. 配置导出只增加账号非敏感描述及池策略，不导 OAuth secret，导入后需要登录。当前配置导出可能包含普通 API Key，因此不能把整个导出文件宣称为“无密钥”。版本升级需读写双方兼容校验，不能只提高 version 字段而任由旧程序忽略 accounts。
8. Provider 复制必须明确：单账号历史行为按兼容要求保留；多账号应显式选择仅配置或复制登录凭据，默认建议仅配置，并提示同一上游账号共用额度。
9. SQLite、PostgreSQL、MySQL、Memory Store 同步更新；SQLite 重建表时核对行数/FK，其他后端保证回填后建立新约束，所有迁移可重入。
10. 按仓库规范更新数据库文档，并使用专用临时空库重新生成 PostgreSQL/MySQL 参考 schema，不能手改生成物。

这是 schema 变更，**不能混用新旧二进制滚动写库**。旧 `WHERE provider_id` 可能操作多行，旧 conflict SQL 也失效。多账号投入使用后不承诺无损降级，回滚需要恢复兼容数据库备份及旧版本程序。

## 十、落地顺序与验收

### A. 账号模型和管理

原表迁移、账号级 CAS/登录/断开、非 Devin 单账号约束、账户面板；先确保旧单账号路径与导入导出/复制语义正确。

### B. 请求调度

显式账号候选、独立 quota/health、Provider 聚合、轮询/优先级/粘性、请求凭据快照、可选并发 lease、全局重试预算，以及 Devin typed error 与安全 failover。

### C. 观测与发布验证

补齐账号 attempt 日志、重启状态、HTTP/IPC 一致性、余额策略说明和跨数据库迁移。后续再做配额加权账号调度或跨实例粘性，不作为首版前置条件。

核心验收场景：

- 添加 B 不覆盖 A，不复制模型绑定；重复凭据不会重复入池。
- 并发登录/退出/回滚不恢复旧授权；跨 Provider 的 account_id 不可操作。
- A 耗尽、B 正常时由 B 服务；全耗尽时安全进入外层 fallback，不忙循环。
- A 失效只要求 A 重登；配额恢复不抹掉独立模型冷却。
- 只有新的权威状态能提前恢复；过期查询、reset 时间经过、网络失败均不能复活账号。
- 同一会话优先固定账号；切换时上游 session 隔离；缺少可重建历史不跨账号续接。
- 明确 HTTP/Connect 拒绝可在安全边界内切换；执行未知或已输出后绝不重放。
- 取消、流结束、超时都释放 lease；请求总尝试数和 deadline 不被多层重试放大。
- 套餐额度优先，reserve 策略明确；UI 不承诺网关可阻止上游自动超额扣费。
- 重启/重复迁移不会恢复已删除凭据或清空已知配额阻塞。
- 同档位等容量账号的份数求和、百分比归一化准确；Pro 有日+周，Max 只有周且不出现虚假日额度。
- 错档位账号不能入池；后台发现档位变化时隔离，单次查询失败不改变已确认档位。
- 耗尽/鉴权失效不会偷偷缩小统计分母；停用/移除等容量变化明确展示；缺少部分账号数据时不输出假完整百分比。
- 日周交叉耗尽时，即使两条汇总条都有剩余，也能正确显示无可用账号；错峰 reset 不显示成共同重置。
- 已知同一上游权益不会因重复 token 被重复计算容量；统一额度展示本身不自动放大 Provider 外层路由权重。

首版验证包含核心库测试、账号/用量/原生转发测试、真实临时 PostgreSQL/MySQL 与 SQLite/Memory 存储合同测试、server 契约测试、core/server/desktop 编译，以及 WebUI 类型检查、聚焦测试、定向 lint 和临时目录构建。全仓 WebUI lint 仍存在未修改文件的既有错误；正式部署及真实账号验收需单独执行。
